1. INTRODUCTION                                 *bindings_explorer-introduction*

`:Bindings` searches and browses the hand-written BINDINGS cheatsheets
under `docs/NOTES/PersonelPlugins/BINDINGS/` and
`docs/NOTES/ExternPlugins/Bindings/` (Keymaps/Usercmds/Autocmds, one file
per plugin). Unlike a live keymap picker (Telescope's own, snacks.picker's
equivalent), these cheatsheets carry rationale, cross-references, changelog
entries and `[default]`/`[custom]` markers that pure `vim.keymap.set`
introspection can never show.

Full feature list with examples: `docs/FEATURES.md` next to this file.

2. COMMANDS                                          *bindings_explorer-commands*

------------------------------------------------------------------------------
2.1 :BINDINGS SEARCH                                    *bindings_explorer-search*

:Bindings search [{plugin}] [{query}]
:Bindings search keymaps|usercmds|autocmds [{plugin}] [{query}]
:Bindings search ... plugin={plugin} [{query}]
    Full-text search across both BINDINGS trees, or one category. Opens a
    live-grep picker via pickers.nvim's engine layer when one is available
    (telescope/fzf-lua/snacks); falls back to a prompt + static list
    (`kit.input` + `kit.select`) otherwise.

    {plugin} narrows the search to one plugin's cheatsheets — see
    |bindings_explorer-plugin-scope| for how a token is recognised as a
    plugin rather than a query, and why order does not matter.

    Examples: >vim
        :Bindings search <leader>iv
        :Bindings search keymaps redact
        :Bindings search autocmds BufEnter
        :Bindings search keymaps hover.nvim
        :Bindings search keymaps hover.nvim zoom
        :Bindings search keymaps plugin=documentat
<

2.2 :BINDINGS BROWSE                                    *bindings_explorer-browse*

:Bindings browse [{plugin}] [{scope}]
:Bindings browse keymaps|usercmds|autocmds [{plugin}] [{scope}]
    ({scope} is "personal" or "extern"; {plugin} is a cheatsheet stem, and
    the two may be given in either order)

    Picker over parsed table ROWS instead of raw text lines. Every `|…|…|`
    line found under the nearest heading becomes a record (scope, category,
    plugin, heading, columns, cells, file, line) — see `records.lua`.
    Selecting a row jumps to its source line.

    Unlike `search`, this slot has no query to be confused with, so a
    prefix resolves here too (`:Bindings browse usercmds documentat`), and
    a token that is neither a scope nor a stem is reported as an error.

    Examples: >vim
        :Bindings browse
        :Bindings browse keymaps
        :Bindings browse keymaps personal
        :Bindings browse usercmds extern
        :Bindings browse keymaps hover.nvim
        :Bindings browse keymaps personal hover.nvim
<

    copies both, newline-separated.

    Examples: >vim

        :Bindings path personal

2.4 :BINDINGS CHECK                                     *bindings_explorer-check*

:Bindings check [{plugin}]
    Read-only drift report between documented Personal bindings and what's
    actually registered right now (`nvim_get_keymap()`/`nvim_get_commands()`).
    No autofix, same stance as casedesk's `:Cases doctor`. Deliberately
    narrow scope — see `drift.lua`'s module doc for the full rationale:

    • Keymaps: documented-but-not-live only (the reverse would flood the
      report with every plugin's own default bindings).
    • Personal only, not Extern.
    • Buffer-local/filetype-scoped keymaps are a known false-positive
      source — `nvim_get_keymap()` only sees GLOBAL maps.
    • Plugins not yet loaded this session (lazy.nvim) are skipped, listed
      by name, not reported as false "missing".
    • Usercmds are checked both directions (much lower noise, since
      `nvim_get_commands({})` never includes vim/plugin defaults).
    • Autocmds are checked both directions too, since 2026-09-02. Forward
      against `nvim_get_autocmds({})`, one finding per documented ROW with
      the events of it that are missing. Backward against lib.nvim's autocmd
      registry, which holds only registrations that went through the helpers
      - Neovim's own and a third-party plugin's are invisible there, which is
      what keeps the reverse direction answerable at all.
    • The corpus counts CALL SITES, `nvim_get_autocmds` counts EVENT
      REGISTRATIONS. Neither number is compared to the other: both sides are
      flattened to (augroup, event) pairs first.
    • A row naming no augroup, or no event Neovim knows, is not checkable.
      Those are counted and reported under the findings, never guessed at.

    {plugin} is the cheatsheet stem and no longer has to be typed exactly
    (|bindings_explorer-plugin-scope|); since this axis filters on
    `rec.plugin == plugin`, it must resolve to exactly one stem.

    Examples: >vim
        :Bindings check
        :Bindings check images.nvim
        :Bindings check images
<

2.5 :BINDINGS CHECK REPO                           *bindings_explorer-check-repo*

:Bindings check repo [{plugin}]
:Bindings check {plugin} repo
:Bindings check repo [{plugin}] root={dir}
    The same report, plus a fourth axis: the plugin's own local checkout.
    Opt-in, off by default.

    "Plugins not yet loaded this session are skipped" (above) is honest but
    empty - skipped is not checked, and in a normal session that is most of
    the personal plugins. For those, the one source that needs no running
    session is the checkout on disk: `repo.lua` searches its .lua/.vim files
    for the documented lhs / command name AS A QUOTED STRING LITERAL.

    New finding kinds `keymap-not-in-repo` / `usercmd-not-in-repo`, in their
    own report section. Points worth knowing before trusting one:

    • A grep, not an API query. An lhs the plugin composes at runtime
      (`prefix .. "m"`) is registered and ungreppable - the known false
      finding of this axis, labelled as such on the section itself.
    • Keymaps are matched case-insensitively (`<Leader>` = `<leader>`),
      command names case-sensitively (folding case makes `:Images` match
      the word "images" throughout images.nvim).
    • Three suppressors: reported only when the literal is in neither the
      plugin's checkout, nor this config's own `lua/` tree, nor the live
      keymaps/commands.
    • A plugin the axis answered for no longer counts as "skipped". One
      with no resolvable checkout, or whose checkout holds no readable
      source, still does.
    • Off by default because it reads ~30 checkouts off disk (measured:
      940ms, 2861 source files, 28 MiB released again at the end of the
      run), unlike the three axes that probe a running session.

    The checkout list comes from `config.repo_dirs()`, whose default calls
    `plugins.personal.export.projects()`; `config.set_repo_dirs()` replaces
    it (the tests use a fixture repo in a temp directory).

    ROOT={DIR} - ONE PATH INSTEAD OF THE PLUGIN LIST

    `root=` points the axis at a collection directory holding several Lua
    projects and takes every one of them (`config.repo_dirs_under`), instead
    of resolving through the Lazy spec. A subdirectory counts as a project
    when it has a `lua/` or a top-level `.lua` file - not when it has a
    `.git`, because this axis reads source, not history. One level deep
    only, or every checkout's own `lua/` and `tests/` would report as
    further "repos".

    `root=` implies `repo`, is position-independent (a `kv` argument; <Tab>
    completes directories) and combines with the {plugin} filter.

    Two things it does that the default resolution cannot: it needs no
    loaded `plugins.personal` layer, and it covers every checkout in the
    path rather than only the ones enabled as plugins. Measured against
    C:/repos: 31 projects resolved, 30 answered, `skipped` 38 -> 8.

    It also adds one report line of its own: projects under the path that
    this corpus does not document at all. That is not drift - no documented
    claim exists to be wrong - but it is the one statement a whole-path
    report can make and a per-plugin report structurally cannot.

    Examples: >vim
        :Bindings check repo
        :Bindings check repo images.nvim
        :Bindings check images.nvim repo
        :Bindings check repo root=C:/repos
        :Bindings check images.nvim root=C:/repos

2.6 :BINDINGS REPORT                                   *bindings_explorer-report*

:Bindings report [{plugin}] [repo] [root={dir}] [out={path}]
    The same run as `:Bindings check`, written to a Markdown file instead of
    a viewer: a run header (date, Neovim version, scope, duration, resolved
    and answered checkouts, skipped count, finding count), a table of the
    findings by kind, and `drift.describe`'s unchanged output as a ```text
    appendix.

    Why it exists: the 2026-09-02 drift report was assembled by hand out of a
    headless run - output redirected, header and counts typed in front of it.
    That hand work is what this route does.

    What it does NOT do is judge the findings. Which of them is a real
    documentation gap and which a tool defect or an expected effect (a
    buffer-local UI that is not open, a lazy trigger that never fired) is a
    reading, and that reading is what a handwritten report is worth writing
    for. This produces the measured half.

    Without `out=`, the report is written to
    `docs/ROADMAP/personal/All/BINDINGS-DRIFT-<date>.md`
    (`config.report_dir()`). `out=` takes a directory (same dated name
    inside it) or a file name (`.md` appended when the extension is
    missing). Typed `PATH`, not `FILE`: `FILE` demands a READABLE file, and
    an output file does not exist yet by definition.

    Examples: >vim
        :Bindings report
        :Bindings report repo
        :Bindings report repo out=C:/tmp
        :Bindings report images.nvim out=C:/tmp/images.md
<

------------------------------------------------------------------------------
2.7 :BINDINGS STATUS                                   *bindings_explorer-status*

:Bindings status
    One page, after the model of `:Reposcope status`:

    • Corpus - files and table rows per root and category, the total, and
      how many rows come from a corpus-level file (`All.md`,
      `Collisions.md`, `Overview.md`) rather than a plugin's sheet.
    • Live in this session - global keymaps split by mode, buffer-local
      keymaps across the open buffers, usercmds, autocmds with group count.
    • Plugins - how many lazy.nvim knows, how many are loaded, and how many
      checkouts the repo axis resolves (or why none).
    • The most recently written `BINDINGS-DRIFT-*.md` in the report
      directory, sorted by name: the name carries the date the report is
      ABOUT, and a file touched later still describes its own day.
    • The route list - the `?`-style cheatsheet for a verb tree that has
      outgrown what completion's `desc` strings show.

    Runs NO drift check. That costs ~650ms across four axes and produces a
    report, which is what `check` and `report` are for; everything here is
    either a cheap live API call or one pass over the corpus (~70ms). A
    dashboard you wait for is a dashboard you open once.

    Examples: >vim
        :Bindings status
<

2.8 PLUGIN SCOPE                                 *bindings_explorer-plugin-scope*

{plugin} is a CHEATSHEET STEM: the filename without `.md`, i.e. `hover.nvim`,
`Gitsigns`, `nvim-config` — the same value `records.lua` carries as its
`plugin` field. `search`, `browse`, `check` and `report` all accept one.
<Tab> in such a slot offers the stems of the category already typed.

A token is matched against the stems in this order:

    1. the stem itself, case ignored (`HOVER.NVIM`);
    2. the same name without the `.nvim`/`nvim-` decoration and without
       separators — `hover` -> `hover.nvim`, `neotree` -> `NeoTree`. This is
       the normalization `drift.lua` already used to map stems onto
       lazy.nvim names; it lives in `plugin_scope.normalize` and is shared,
       so `:Bindings search dap` and `:Bindings check dap` cannot disagree;
    3. ONLY in the `plugin={prefix}` form: prefix matching
       (`plugin=documentat` -> `documentation.nvim`). A prefix naming more
       than one stem is an error listing them, never a guess.

One token may name several sheets, and that is not an error: `dap` is
`Keymaps/dap.nvim.md` (personal) and `Keymaps/Dap.md` (extern) — one plugin,
documented from both sides, and a search over both is what was asked for.
Only `check`/`report` need exactly one stem (they filter on
`rec.plugin == plugin`); there an exactly typed name beats its normalized
twin, and a genuinely ambiguous token is reported rather than narrowed.

Why prefixes do not apply to `search`: its first positional carries a scope OR
a query — `:Bindings search keymaps redact` was a text search before scopes
existed and still is. So only a token that NAMES a sheet counts as a scope.
Position does not matter (`hover.nvim zoom` and `zoom hover.nvim` are the same
request), and two tokens of which neither names a sheet are a typo, not a
two-word query — one pattern is searched for, never two. To search for a
plugin NAME as text, type it into the picker instead of the command line.

3. ARCHITECTURE                                 *bindings_explorer-architecture*

Module: `lua/bindings/usrcmds/bindings_explorer/`

  • config.lua   - the two BINDINGS roots, and per-category subpaths
  • search.lua   - static substring search (Phase 1 fallback)
  • live.lua     - live-grep via pickers.nvim's engine layer (Phase 1)
  • ui.lua       - kit.select wiring for search.lua's hits
  • plugin_scope.lua - cheatsheet stem -> files, for every {plugin} slot
  • records.lua  - tolerant table-row scraper (Phase 2)
  • browse.lua   - kit.select wiring for records.lua's rows
  • drift.lua    - documented-vs-live comparison (Phase 3)
  • source.lua   - what this config's source registers, from module_map.json
  • repo.lua     - "is this literal in that checkout's source" (repo axis)
  • report.lua   - the same report as a Markdown file (Phase 4)
  • status.lua   - the dashboard (Phase 4)
  • init.lua     - composer verb ":Bindings" + all routes
